TeamFlow — Multi-Tenant SaaS Platform

Domain: Team & Project Management
Architecture Style: Modular Monolith (service-ready)
Target Users: Small–mid sized teams, startups, internal org tools

1. High-Level Overview

TeamFlow is a production-grade multi-tenant SaaS platform where multiple organizations can:

Register and manage teams

Subscribe to paid plans

Access features based on subscription tier

Track work via projects and tasks

View usage analytics

Receive real-time notifications

The system is designed to simulate a real startup backend, focusing on correctness, security, scalability, and maintainability rather than UI polish.

2. Core Design Principles

These are intentional decisions, not accidents.

Single codebase, multiple tenants

All organizations share infrastructure

Data isolation is enforced at the application & query level

Subscription-driven feature control

Business logic determines access, not frontend flags

Backend is the source of truth

Fail-safe over fail-open

Payment or webhook failures never silently grant access

Defaults restrict access until state is confirmed

Production realism

Logging, pagination, rate limiting, and deployment are first-class

Designed assuming things will fail

3. System Architecture
Logical Architecture

Frontend: React SPA

Backend: REST API (NestJS-style layered architecture)

Database: PostgreSQL (primary data store)

Cache & infra support: Redis

External services: Stripe (payments), Email provider

Transport: HTTPS + WebSockets

Backend Layers

Controller (request validation, auth guards)

Service (business logic)

Repository (DB access)

Infrastructure (Redis, Stripe, WebSockets)

This separation makes it:

Testable

Refactorable into microservices later

Easy to reason about during reviews

5. Multi-Tenancy Model (Critical Section)
Approach Chosen

Shared database, shared schema, tenant-scoped rows

Every core table includes:

organization_id (FK)

Enforcement Strategy

organization_id is derived from:

JWT claims

Active organization context

Never accepted blindly from client input

All queries are scoped explicitly

Why Not Separate Databases?

Higher operational complexity

Poor fit for early-stage SaaS

Harder analytics and admin visibility

Risk Mitigation

Query guards

Foreign key constraints

Indexed organization_id

Defensive programming in repositories

This is the most common real-world SaaS approach.

6. Subscription & Billing System
Plans

Free: Limited projects

Pro: Unlimited projects

Enterprise: Analytics + real-time features

Payment Flow

User selects plan

Redirected to Stripe Checkout (test mode)

Stripe sends webhook events

Backend verifies event signature

Subscription state updated internally

Webhook-Driven Truth

Stripe is not trusted blindly:

All events verified

Idempotency enforced

Subscription state stored locally

Feature Gating

Backend checks subscription tier

Frontend only reflects backend decisions

No client-side trust
